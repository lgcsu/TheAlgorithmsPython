## 1. Bug

- Original line 63: `return 1 if n == 0 else math.floor(math.log10(abs(n)) + 1)`
- Digit count: d(n) is the unique integer with `10^(d-1) <= n < 10^d`, i.e. `d = floor(log10 n) + 1`
- Formula is right, float arithmetic is not exact; just below a power of ten the result rounds up to a whole number -> count is one too high
- Issue text quotes `math.log(abs(n), 10)`; master already uses `math.log10`, bug still there

## 3. Why it fails

- Smallest failing input: `10**15 - 2 = 999999999999998`
  - observed as the lowest failure near `10^15`; "smallest overall" relies on `10**k - 1` being right for k <= 14 plus log10 being monotonic (reasoned, not swept)
- Three rounding steps, any one is enough:
  1. log10 result rounding
     - `log10(10^k - m) ≈ k - m / (10^k · ln 10)`
     - doubles in [8, 16) are spaced `2^-49 ≈ 1.78×10^-15`, half-spacing `8.88×10^-16`
     - m = 2, k = 15: deficit `8.69×10^-16` < `8.88×10^-16` -> rounds to exactly 15.0 (experiment G)
     - m = 3, k = 15: deficit `1.30×10^-15` > half-spacing -> stays below 15 (experiment C)
     - below `2^53`, so int -> float is exact here; this step alone causes it
  2. int -> double conversion
     - above `2^53 ≈ 9.007×10^15` not every int is a double; `float(10**16 - 1) == 1e16` (experiment G)
  3. the float `+ 1`
     - proposed reason the k = 16 band is 61 wide: log lands one ulp under 16, adding 1 moves into [16, 32) where spacing doubles, tie rounds to 17.0
     - band width is observed (experiment E); this mechanism is reasoned only
- Original only ever over-counted in what was tested; not swept on arbitrary inputs

## 5. Fix (lines 91-104)

```python
    if n == 0:
        return 1
    n = abs(n)
    # log10() works in floating point, so close to a power of ten the estimate
    # can be off by one: the exact integer comparisons below correct it.
    digits = math.floor(math.log10(n)) + 1
    upper_bound = 10**digits
    while upper_bound <= n:
        digits += 1
        upper_bound *= 10
    while upper_bound // 10 > n:
        digits -= 1
        upper_bound //= 10
    return digits
```

- Invariant: `upper_bound == 10^digits`
- After loop 1: `n < 10^digits`; terminates because `upper_bound` grows tenfold per pass
- Loop 2: only steps down when `10^(digits-1) > n`, so the first bound survives; terminates because `n >= 1 = 10^0`
- Exit: `10^(digits-1) <= n < 10^digits` = definition of d(n), unique -> exact regardless of estimate quality
- Float accuracy only affects loop count (0 or 1 pass in practice)
- Cost for a d-digit n: one big-int power + O(d) compares; O(1) for machine-size ints; `num_digits` is Θ(d²) for big ints
- First draft used `10**digits` / `10 ** (digits - 1)` inside the loop conditions; replaced by the running `upper_bound` so the power is computed once
